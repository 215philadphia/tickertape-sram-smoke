## How it works

TickerTape-Out is a protocol emulator built from two programmable finite state transducers (PFSTs).
Each core is a table-driven state machine whose transition table lives in its own IHP 256x32 SRAM macro:
every row it fetches sets the next state, four output pins, a wait time, and one datapath operation
(hold, shift, load from a 3-byte TX FIFO, save to a scratch register). The address of the next row is the
current state plus two input bits chosen per row, so a protocol is firmware: UART, SPI and I2C are tables,
not hardware blocks. A host loads tables and configuration over an SPI port; core 0's saved byte feeds a
comparator whose result core 1 can branch on, so the two cores can react to each other without the host.

Every row lasts exactly P x (1 + wait) clock cycles.

Two features make it a literal bump-in-the-wire and let it drive bidirectional buses. Any of uo_out[5:0] can
forward an input pin (UOMAP bit 7): directly, with only gate delay, or through a 2-flop synchronizer (1-2 clock
cycles), while a core parses the same line. And a pin in PINMODE 3 is driven only in rows whose direction bits
say so, so a program can turn a line around mid-transaction. Half-duplex serial on a single wire is demonstrated; other shared-wire
protocols such as SWD need the same kind of turnaround. The SRAM returns data one cycle after the address, so the next row is read
in the last cycle of the current one.

## How to test

Host SPI is mode 0, MSB first, on ui_in[4] SCK, ui_in[5] MOSI, ui_in[6] CS_n, with MISO on uo_out[7]; keep SCK
at or below 4 MHz with a 50 MHz clock. Commands (c is the core number, 0 or 1): 0x01 WRITE_REG addr, data...;
0x02 READ_REG addr, dummy...; 0x10+c WRITE_TABLE row, 4 bytes per word...; 0x20+c READ_TABLE; 0x30+c TX_PUSH;
0x40+c CTRL (bit 0 RUN, bit 1 RESTART); 0x50+c READ_SCR. Load a table while the core is stopped, set P, CFG, RSEL, pin
modes and OUT_INIT, then send CTRL with RUN and RESTART.

The chip is powered down when its design is deselected and loses its tables and registers, so the host must reload
them each time the design is selected, and after any reset (rst_n). Tables come from the OCaml toolchain in model/ (run
model/run_tests.sh to produce compiled_tables.json; see docs/toolchain.md).

The cocotb tests in test/ (17 in all) drive the chip only through these pins, as the demo board's microcontroller
would. test_pfst.py checks the chip's features. test_programs.py loads each program compiled by the toolchain onto the
chip and decodes the pins: UART transmit and receive, SPI transmit, I2C write, half-duplex UART on one wire, a PS/2
receiver, an SPI target, and a two-core price watcher in which core 0 receives prices and core 1 sends an SPI order when a price falls
below a threshold. test_ethernet.py runs parts of 10BASE-T Ethernet with a 40 MHz clock: link test pulses, a Manchester
transmitter and a frame-start detector (docs/ethernet.md); the chip cannot send or receive a full Ethernet frame.

## External hardware

None required for the tests: the demo board's RP2350 can act as the SPI host. Protocol pins are uio[3:0] for
core 0 and uio[7:4] for core 1; open-drain lines (I2C) need pull-ups, and a CS line should have a pull-up so it
idles high before the chip is configured.

Pins used by each demonstrated program (all I/O is 3.3 V; the tests drive these pins directly, nothing here has been
connected to a real device yet):

| Program | Chip pins | External parts |
|---|---|---|
| UART TX | TX on uio[0] (core 0) | USB-UART adapter RX to uio[0], common ground |
| UART RX | RX on any input chosen by INMAP; the tests use uio[4] and uio[0] | USB-UART adapter TX, 3.3 V |
| SPI controller | CS_n uio[2], SCK uio[1], MOSI uio[0] | A 3.3 V SPI device; a pull-up on CS_n |
| SPI target | MOSI ui_in[0], SCK ui_in[1], CS_n ui_in[2] in; MISO uio[0] out, released while CS_n is high | A 3.3 V SPI master; MISO shares a bus, so no pull-down on it; SCK at or below about 4 MHz with a 50 MHz clock |
| I2C write | SDA uio[0], SCL uio[1], both open drain (the chip only pulls low) | **Pull-ups to 3.3 V on SDA and SCL, 2.2 to 4.7 kOhm**; a 3.3 V target |
| PS/2 receiver | DATA uio[0], CLK uio[1], both inputs; the chip only receives | A PS/2 keyboard or mouse uses 5 V open-collector lines: a **level shifter to 3.3 V and pull-ups** are needed. Untested on a real device |
| Half-duplex UART | One wire on uio[0] in PINMODE 3 (driven only while transmitting) | Pull-up on the wire; the far end must release it when the chip transmits |
| Nano-Tick (both cores) | Prices in on uio[0] (UART); SPI order out on uio[6:4] (CS_n, SCK, MOSI) | USB-UART or the RP2350 as the price source; optional logic analyzer on uio[6:4] |
